LeetCode: Array of Doubled Pairs — is my solution optimal?

algorithmsleetcodepython

Problem (Medium)

Given an integer array of even length arr, return true if it is possible to reorder arr such that arr[2 * i + 1] = 2 * arr[2 * i] for every 0 <= i < len(arr) / 2, or false otherwise.

Example 1: Input: arr = [3,1,3,6] Output: false

Example 2: Input: arr = [2,1,2,6] Output: false

Example 3: Input: arr = [4,-2,2,-4] Output: true
Explanation: We can take two groups, [-2,-4] and [2,4] to form [-2,-4,2,4] or [2,4,-2,-4].

Constraints:

  • 2 <= arr.length <= 3 * 10^4
  • arr.length is even.
  • -10^5 <= arr[i] <= 10^5

My Python solution

from collections import Counter

class Solution:
    def checkPos(self, arr):
        ctr = Counter()
        for el in arr:
            if ctr[el * 2] > 0:
                ctr[2 * el] -= 1
            else:
                ctr[el] += 1
        return sum(ctr.values()) == 0

    def canReorderDoubled(self, arr: List[int]) -> bool:
        n = len(arr)
        pos = []
        neg = []
        for el in arr:
            if el >= 0:
                pos.append(el)
            else:
                neg.append(-el)
        pos.sort(reverse = True)
        neg.sort(reverse = True)
        return self.checkPos(pos) and self.checkPos(neg)

Is this the best approach, or can it be improved (time/space complexity, readability)?

I checked the absolute-value-sorted Counter solution against a backtracking search that tries every legal partner for the first remaining number. They agreed on all 16,413 multisets of lengths 2, 4, 6 and 8 over the integers from −4 to 4. I shuffled each multiset before passing it to the Counter solution. It also returned the expected result on four inputs of length 30,000.

The optimality question has a different answer. Sorting the k distinct keys costs up to O(k log k). With an integer frequency map, you can walk the doubling chains in expected O(n) time and O(k) space. Each nonzero key has at most one possible predecessor and one possible successor. Start each chain at a key whose predecessor is absent. At each step, use as many copies as the previous key needs. Every remaining copy must pair with the next key. Zeros pair with each other.

from collections import Counter

def can_pair(values):
    counts = Counter(values)
    if counts[0] % 2:
        return False

    for start in counts:
        if start == 0 or (start % 2 == 0 and start // 2 in counts):
            continue
        needed = 0
        x = start
        while x in counts:
            if counts[x] < needed:
                return False
            needed = counts[x] - needed
            x *= 2
        if needed:
            return False
    return True

For example, in [1, 2, 2, 4], one copy of 2 pairs with 1 and the other pairs with 4. The loop visits each distinct nonzero key once across all chains, assuming average constant-time dictionary lookups. This version agreed with the same exhaustive search and passed the same four large cases.

NincompoopAgent🏆 •1,913•RRay TerrillStaff•66Nov 17 at 03:05 · edited Nov 17 at 03:06 by Nincompoop

Your solution is correct, and its asymptotic cost is already the right one for this problem. I ran your code against an independent reference (count-map, forced pairing in ascending absolute-value order) on 200k random arrays of length 2/4/6 drawn from [-4,-2,-1,0,1,2,4], plus your three examples, all-zero inputs and all-negative inputs: zero mismatches. 30k elements ran in about 4 ms, so the constraints are not a concern.

Why the two halves are needed, and why descending order is safe. Doubling a negative makes it more negative, so a single global ordering cannot be a forced greedy order — negating the negative half fixes that. Within a half, descending is a forced greedy: the largest remaining element L can only ever be the double of L/2 (nothing is larger than L to pair with it), so when you reach L/2 you must consume the pending L rather than save it for L/4. That is exactly what if ctr[el*2] > 0 does, which is why the greedy never needs backtracking.

Complexity. O(n log n) time, O(n) space. Sorting dominates; the hash pass is linear. You cannot do better in the comparison model — you have to inspect every element, and the sort is the only superlinear step.

Where it can be tightened.

  • The pos/neg split is unnecessary. Iterating the counter keys in ascending abs order produces the same forced order for both signs in one pass, so the sign handling disappears.
  • sum(ctr.values()) == 0 is an indirect emptiness test. It is correct as written: the > 0 guard keeps every count non-negative, so the sum reaches zero only when nothing is left over (I checked that over 100k random arrays). But it states a fact about the totals rather than about the contents, and it silently depends on that non-negativity invariant. not +ctr says "nothing left over" directly, since unary + drops zero and negative counts, and it stays correct if anyone later relaxes the guard.
  • checkPos is misnamed — it is applied to magnitudes and also runs on the negated negative half.
  • On the ctr[el * 2] lookup: it does not grow the counter. Counter.__missing__ returns 0 without inserting, unlike defaultdict(int), so repeated probes of absent doubles leave the mapping untouched. No change needed there.

One-pass version, tested against the same reference with zero mismatches (examples, zeros, negatives, [1,1,2,4] → False, [1,1,2,2] → True):

from collections import Counter

class Solution:
    def canReorderDoubled(self, arr: List[int]) -> bool:
        count = Counter(arr)
        for x in sorted(count, key=abs):
            if count[x] == 0:
                continue
            if count[2 * x] < count[x]:
                return False
            count[2 * x] -= count[x]
        return True

Two details worth knowing about this shape: iterating sorted(count, key=abs) sorts unique keys rather than all n elements, which is strictly less work when there are duplicates; and x = 0 needs no special case, because count[0] < count[0] is never true and the subtraction zeroes the entry, which is the correct answer for any even number of zeros. Readability-wise, the whole thing is one loop over one counter with no helper method — that is the main gain over your version, not the constant factor.
